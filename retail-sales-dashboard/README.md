# Retail Sales & Customer Analytics Dashboard

A small end-to-end data project: a fictional retail company's SQLite database,
10 business-question SQL queries, and a Python/pandas layer that turns those
queries into charts.

## Project structure

```
retail-sales-dashboard/
├── data/
│   └── retail.db              # generated SQLite database (not committed if large — see .gitignore note below)
├── sql/
│   ├── schema.sql              # table definitions
│   └── queries.sql             # the 10 business questions
├── python/
│   ├── build_database.py       # generates & seeds retail.db
│   └── analysis.py             # runs queries via pandas, saves charts
├── charts/                     # PNG output from analysis.py
├── requirements.txt
└── README.md
```

## Schema

```
customers (customer_id PK, first_name, last_name, city, state, age)
products  (product_id PK, product_name, category, price)
orders    (order_id PK, customer_id FK, order_date, total_amount)
order_items (order_item_id PK, order_id FK, product_id FK, quantity)
```

`customers → orders → order_items → products` — a standard one-to-many /
many-to-many pattern that mirrors how real e-commerce schemas are shaped.

## How to run it

**1. Clone and set up a virtual environment**

```bash
git clone <your-repo-url>
cd retail-sales-dashboard
python3 -m venv venv
source venv/bin/activate      # on Windows: venv\Scripts\activate
pip install -r requirements.txt
```

**2. Build the database**

```bash
python python/build_database.py
```

This creates `data/retail.db` with 120 customers, 45 products, 400 orders,
and ~1,200 order line items — enough volume for the aggregates to look
realistic without needing a real dataset.

**3. Run the SQL directly (optional)**

If you have the `sqlite3` CLI installed:

```bash
sqlite3 data/retail.db
sqlite> .read sql/queries.sql
```

Or open `data/retail.db` in any SQLite GUI (DB Browser for SQLite, TablePlus,
the SQLite extension in VS Code, etc.) and run `sql/queries.sql` query by
query.

**4. Run the Python analysis + generate charts**

```bash
python python/analysis.py
```

This prints each query's results as a pandas DataFrame and saves four charts
to `charts/`:
- `revenue_by_category.png`
- `monthly_revenue.png`
- `top_10_products.png`
- `top_10_customers.png`

## The 10 business questions answered

1. What are the 10 most expensive products? — `ORDER BY`, `LIMIT`
2. What is total revenue? — `SUM()`, `JOIN`
3. Revenue by product category — `GROUP BY`, `SUM()`
4. Which customers have spent the most? — multi-table `JOIN`
5. Monthly revenue — `strftime()` date bucketing
6. Top 5 products by revenue
7. Top 10 customers by spending (with order counts)
8. Which category has the highest average order value? — subquery + `AVG()`
9. Customers with no order in the last 90 days — `LEFT JOIN` + `HAVING`
10. What % of revenue comes from the top 10 customers? — CTE + window function (`ROW_NUMBER()`)

All queries live in `sql/queries.sql` with comments explaining the SQL
concept each one practices.

## What I'd talk about in an interview

Query #10 is the most interesting one: it uses a CTE and a window function
(`ROW_NUMBER() OVER (ORDER BY total_spent DESC)`) to rank customers, then
sums the top 10 against the grand total to get a revenue-concentration
percentage — a real metric retail and SaaS businesses track (often called
customer concentration risk).

## Notes on the data

The database is generated by `python/build_database.py` using a fixed random
seed, so results are reproducible. No external data source or API key is
needed — customer names, cities, and product names are drawn from static
lists in that script, and order dates/amounts are randomized with a slight
weighting so a handful of "power customers" naturally emerge (which is what
makes questions #4, #7, and #10 interesting instead of flat).
